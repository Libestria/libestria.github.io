Introduction

NIP-05 est une convention du protocole Nostr permettant de relier une clé publique à une adresse lisible, par exemple alice@exemple.fr. Vous pouvez la configurer sur un domaine que vous contrôlez, sans abonnement à un fournisseur NIP-05.

Prérequis : un profil Nostr et sa clé publique, un domaine sous votre contrôle et un hébergement HTTPS permettant de publier un fichier JSON et de configurer les en-têtes HTTP. Les manipulations dépendent de l’hébergeur.

À savoir : NIP-05 associe une clé à un domaine ; il ne certifie pas l’identité civile de son titulaire et n’est pas obligatoire pour utiliser Nostr.

1. Choisir son adresse NIP-05

Choisissez un identifiant tel que alice@exemple.fr. La partie avant @ doit utiliser uniquement les caractères a-z, les chiffres 0-9, le tiret, le souligné ou le point.

Pour associer directement le domaine à votre profil, vous pouvez choisir _@exemple.fr. Certains clients l’affichent alors comme exemple.fr.

Le domaine choisi doit être exactement celui qui hébergera le fichier, sans préfixe www sauf si votre identifiant contient lui-même ce sous-domaine.

2. Récupérer la clé publique au format hexadécimal

  1. Ouvrez votre client Nostr et recherchez la clé publique de votre profil.
  2. Si elle commence par npub1, utilisez par exemple le convertisseur NostrCheck (npub ↔ HEX — EN), ou l’option d’export hexadécimal de votre client si elle existe. Copiez uniquement votre clé publique npub dans le champ prévu, puis récupérez la valeur HEX.
  3. Vérifiez que le résultat contient exactement 64 caractères hexadécimaux (chiffres 0-9 et lettres a-f).
Sécurité : n’utilisez jamais votre clé privée nsec1… et ne la collez dans aucun convertisseur ou formulaire. Seule la clé publique doit apparaître dans le fichier.

3. Créer le fichier nostr.json

Créez un fichier texte nommé exactement nostr.json. Remplacez VOTRE_CLE_PUBLIQUE_HEX_64_CARACTERES par votre véritable clé publique hexadécimale :

{
  "names": {
    "alice": "VOTRE_CLE_PUBLIQUE_HEX_64_CARACTERES"
  }
}

Le contenu présenté est un gabarit : la valeur de remplacement n’est pas une clé valide. Pour l’identifiant _@exemple.fr, remplacez la clé JSON "alice" par "_".

Pour enregistrer plusieurs noms sur le même domaine, utilisez ce second gabarit dans le même fichier nostr.json :

{
  "names": {
    "alice": "CLE_HEX_ALICE_64_CARACTERES",
    "bob": "CLE_HEX_BOB_64_CARACTERES",
    "association": "CLE_HEX_ASSOCIATION_64_CARACTERES",
    "_": "CLE_HEX_DOMAINE_64_CARACTERES"
  }
}

Remplacez chaque valeur d’exemple par la clé publique HEX de 64 caractères correspondant au nom. Les adresses seront alice@exemple.fr, bob@exemple.fr, association@exemple.fr et _@exemple.fr. La dernière entrée, "_", est facultative et permet d’associer le domaine lui-même à un profil.

À retenir : utilisez un seul objet "names" dans le fichier, séparez les entrées par des virgules (sauf la dernière) et ne laissez aucune valeur fictive lors de la publication. Plusieurs noms peuvent pointer vers une même clé publique si c’est volontaire.

Option avancée : déclarer des relais. La spécification permet d’ajouter un objet "relays" facultatif. Chaque entrée associe une clé publique hexadécimale à une liste d’URL de relais wss:// où les clients peuvent rechercher les événements du profil. Voici un gabarit réunissant plusieurs noms et leurs relais dans un seul fichier nostr.json :

{
  "names": {
    "alice": "HEX_ALICE_64_CARACTERES",
    "bob": "HEX_BOB_64_CARACTERES"
  },
  "relays": {
    "HEX_ALICE_64_CARACTERES": [
      "wss://relay.exemple.net",
      "wss://relay2.exemple.net"
    ],
    "HEX_BOB_64_CARACTERES": [
      "wss://relay.exemple.net"
    ]
  }
}

Remplacez les clés fictives par les mêmes valeurs hexadécimales de 64 caractères dans "names" et dans les clés de "relays". Remplacez également les URL de démonstration par celles des relais que vous utilisez réellement. Un profil peut avoir plusieurs relais, et plusieurs profils peuvent partager un relais.

À savoir : "relays" est facultatif : son absence n’empêche pas la vérification NIP-05. Il ne faut pas confondre ces indications de découverte avec une garantie de disponibilité des événements sur les relais.

4. Publier le fichier sur son domaine

  1. Connectez-vous à l’espace de gestion des fichiers de votre hébergement, ou utilisez votre méthode habituelle de déploiement.
  2. À la racine publique du site correspondant à exemple.fr, créez le dossier .well-known s’il n’existe pas.
  3. Déposez nostr.json dans ce dossier, à l’emplacement public /.well-known/nostr.json.
  4. Vérifiez que le fichier est servi par HTTPS sans authentification ni redirection.

Testez dans votre navigateur : https://exemple.fr/.well-known/nostr.json?name=alice. Le navigateur doit afficher une réponse JSON valide, et non une page HTML ou une erreur 404.

Sur certains CMS, hébergements statiques ou configurations de sécurité, les dossiers commençant par un point peuvent être ignorés ou bloqués. Vérifiez leur publication effective dans votre environnement.

5. Autoriser l’accès CORS

Les clients Nostr fonctionnant dans un navigateur doivent pouvoir consulter le fichier depuis une autre origine. Configurez votre serveur pour envoyer l’en-tête HTTP suivant sur /.well-known/nostr.json :

Access-Control-Allow-Origin: *

La méthode dépend de l’hébergement (Apache, Nginx, CDN ou plateforme statique). Servez le fichier avec le type de contenu application/json.

Important : le point d’accès NIP-05 ne doit pas renvoyer de redirection HTTP, y compris vers une autre variante du domaine. Configurez directement la bonne adresse HTTPS.

6. Enregistrer l’identifiant dans son profil Nostr

  1. Ouvrez les réglages de votre profil dans votre client Nostr.
  2. Recherchez le champ correspondant à l’identifiant « NIP-05 » ou à l’adresse de vérification (son nom varie selon le client).
  3. Saisissez alice@exemple.fr, ou _@exemple.fr si vous avez choisi la variante racine.
  4. Enregistrez ou publiez la modification du profil, puis attendez que votre client et ses relais la prennent en compte.

Le champ NIP-05 est publié dans les métadonnées du profil Nostr (événement de type 0). Certains clients ne permettent pas de le modifier directement : dans ce cas, utilisez un client compatible avec l’édition de ce champ.

7. Vérifier que la configuration fonctionne

  1. Ouvrez l’URL https://exemple.fr/.well-known/nostr.json?name=alice.
  2. Vérifiez que names.alice correspond exactement à la clé publique hexadécimale de votre profil.
  3. Dans les outils de développement du navigateur, ou avec la commande curl -i ci-dessous, vérifiez la réponse HTTPS, l’absence de redirection et l’en-tête CORS.
  4. Consultez votre profil depuis un client Nostr compatible NIP-05 et vérifiez que l’identifiant est reconnu.
curl -i 'https://exemple.fr/.well-known/nostr.json?name=alice'

La réponse doit être 200 OK avec un JSON valide et l’en-tête Access-Control-Allow-Origin: *. L’affichage d’une coche dépend du client et peut être différé par son cache.

8. Résoudre les problèmes courants

  • Erreur 404 : vérifiez l’emplacement et la publication du dossier .well-known.
  • JSON invalide : contrôlez les guillemets doubles, les virgules et l’absence de commentaires.
  • Clé incorrecte : utilisez 64 caractères hexadécimaux en minuscules, jamais npub.
  • Échec dans un client Web : vérifiez l’en-tête CORS et les éventuelles redirections.
  • Identifiant non reconnu : vérifiez la correspondance exacte entre le nom demandé, le fichier et le champ NIP-05 du profil.

9. Checklist finale

Conclusion

Votre domaine peut maintenant servir d’identifiant Nostr lisible, tant que vous contrôlez le domaine et maintenez le fichier accessible. Gardez votre hébergement HTTPS actif et contrôlez la correspondance après tout changement de clé, de domaine ou de configuration serveur. Votre clé publique reste l’identifiant de référence dans le protocole Nostr.
